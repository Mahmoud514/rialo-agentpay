01 · The Premise

AI can act.
Now it can pay.

Agents already browse, negotiate, buy compute and call APIs. What they could not do was settle — hold a real wallet and move real value under rules their operator controls. AgentPay closes that gap: an identity-bound wallet, programmable payment policy, and on-chain settlement on Rialo.

03 · Task Marketplace

Work gets done.
Payment follows proof.

The marketplace closes the loop between a human who needs work and a worker who can do it. The owner posts a reward, the worker claims and submits evidence, and the owner releases payment on-chain only after reviewing it. Reject the work and no payment is made.

01Owner

Post a task

Set the brief, the acceptance criteria, the reward in RLO, and the agent that will pay on approval.

reward reserved
02Worker

Claim the work

A different account claims the open task and chooses the Rialo payout address the owner will see before approving.

one worker at a time
03Evidence

Submit proof

Add notes and attach deliverables — text, PDF, images, archives, or any other browser-readable file type. Only the two parties can read them.

text + any file
04Owner

Approve or reject

Approve to release the reward on-chain and return the transaction signature. Reject to close the task with no transfer and no payout.

payment follows approval
Role gates Server-enforced
  • An owner cannot claim, submit, or review their own task as the worker.
  • A worker cannot approve or reject — payout authority belongs to the owner.
  • No payment is sent before the owner approves the submitted evidence.
  • The public board hides terminal tasks; task detail is limited to the two parties.
  • In-page toasts tell the owner when work is submitted and the worker when it is paid or rejected.
  • The owner sees the worker's payout address before pressing approve.

04 · Architecture

Identity in.
Signature out.

Everything on this page is pinned to the system as it ships today: the real flow from GitHub identity to on-chain settlement, the core route groups behind each page, and every page it actually serves. No placeholders, no simulated data.

GitHub Identity
OAuth anchors every wallet to a verified GitHub account. One session mechanism: opaque cookie + server-side map.
/auth/github
AgentPay Session
Session-scoped user + wallet state. The browser never holds key material.
GET /api/me
Your Wallet
One persistent Rialo keypair per GitHub user id, created and held server-side (mode 600). The public address is shown; the key never leaves the server.
wallet per user id
Your Agents
Separate entities owned by your account. Each receives an isolated signing identity; private keys stay behind a hardened signer boundary. Metadata mirrors only the public address. Lifecycle, policy, and payment gates are enforced server-side.
isolated signer identity
Payment Policy
Versioned limits (per-transaction, daily) plus recipient and action allow-lists. Every unset limit and empty list denies — policy is read-only data checked before any transfer.
deny-by-contract
Rialo
The settlement layer: balances, direct transfers, and the deployed Venus payment program — the program path stays disabled behind an explicit operator cap. One RPC configuration; one CLI signing path. Agent payments may optionally pass through an opt-in, env-configured Latch transport/policy gate in front of that same CLI-signed path — it never replaces the signing path, never holds key material, and stays fully inactive unless explicitly enabled.
testnet RPC · Venus
Recipient
Any Rialo address: another agent, a service, or a human wallet. Every settlement returns a real transaction signature.
32–44 char address

10 · FAQ

What is real,
what is next.

AgentPay is a payment layer for autonomous software, with a two-sided task marketplace on top. A human identity (verified by GitHub) gets a persistent Rialo wallet; agents created under that account each receive an isolated signing identity, and can initiate payments through AgentPay's API that settle on-chain. In the marketplace, an owner posts a rewarded task, a worker submits evidence, and the owner approves the payout — or rejects it with no transfer. Today it runs on Rialo Testnet.
On first login, AgentPay provisions one Rialo keypair bound to your GitHub identity and stores it server-side with restricted file permissions. Your wallet address is visible at all times; your balance is read live from the Rialo RPC. If the RPC is down, the wallet shows an explicit "unavailable" state — it never invents a zero.
Human payments: POST /api/payment validates the recipient and amount, pre-checks the balance, signs the transaction from your wallet, and returns the real transaction signature. Agent payments use a dedicated lane: POST /api/agents/triggers/payments enables autonomous credential-authenticated payments, while POST /api/agents/{id}/payments allows owner-initiated transfers. Both route through the hardened signer and produce signed on-chain transfers. A deployed Venus payment program exists for program-mediated settlement; that path stays disabled until an operator explicitly enables it with a spending cap.
Rialo is the blockchain AgentPay settles on. It exposes a standard node RPC (block height, balances, transfers) and executes PolkaVM programs written in the Venus workflow language — the layer AgentPay's program-mediated payments target.
Agents can initiate real payments today through the documented API endpoints — owner-initiated via the session, or credential-authenticated via the trigger lane. Policy enforcement is live on every payment: lifecycle gate, recipient and action allow-lists, per-transaction and daily limits — all deny-by-default, checked before any transfer. Each agent has a distinct isolated signing identity, funded by its owner; there is no automatic funding path — a 0-balance agent stays INSUFFICIENT_FUNDS until funded.
GitHub identity and sessions, your persistent wallet, the Testnet faucet (your wallet), direct on-chain payments with returned signatures, agent payments with the full policy gate chain (owner- or credential-initiated), each agent's isolated signing identity, reconciliation, per-agent activity and owner statistics, the owner-scoped leaderboard, public verification with per-agent proof listings, read-only health/program probes, and the live task marketplace — claim, submission with notes and any file type, owner review, approve-and-pay, reject-without-payment, and in-page outcome notifications for the worker. The Live Network section on this page reports those states from real endpoints.
Program-mediated payments (built, deployed, and verified — but disabled behind the explicit operator safety cap); credential issuance remains an operator act through the store module (authentication, rotation, and revocation are enabled over the thresholded ops endpoint). Notifications are in-page only — there is no email, push, or after-page-close delivery, and no global public transaction feed. A missing wallet key is recovered only through the explicit zero-balance recovery path; a funded wallet is never silently replaced. The Leaderboard and Recent Activity sections on this page keep their honest empty states: the owner-scoped leaderboard and per-agent activity are live at /leaderboard.html and /activity.html, but a shared public feed does not exist — no placeholder agents, no sample transactions.
